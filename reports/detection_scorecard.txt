4. THE ONE REAL GAP
------------------------------------------------------------------------------
duplicate_customer_id is the only defect below 100% recall.

13 rows carrying a planted duplicate id reached the output without
the dedup check firing. The cleaned file nonetheless contains zero
duplicate ids, because the other row holding each id had already
been quarantined for an unrelated reason - so no collision existed
for the check to find.

The output is correct, but the property is fragile: dedup recall
depends on how much the preceding stage happened to quarantine.
Relaxing nullability as section 4 of the cleaning log describes
would keep those rows and surface 13 genuine collisions that
currently never meet. Uniqueness must therefore be enforced at the
output, which post-validation does, and not left to a scan whose
reach shifts with upstream policy.
